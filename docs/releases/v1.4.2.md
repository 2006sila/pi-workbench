## 二、为什么加这两样

极简模式把 65 个模块压成「一张菜单 + 按需读模块」。原来菜单只有「模块 | 何时用」两列：

- 类目内多个模块同时命中时，**没有第二判据**；
- 模块越多，那张表越长，模型每次读菜单都要把整张表读完。

于是：

- **评分列**：每行带 `x/10`，排序变成 **任务匹配度 → 评分 → 索引序**。
- **分片**：类目内模块数超过阈值（默认 12）→ 该类拆到 `sections/<NN>-<模块id>.md`，
  菜单里只留一行指针。每次重新部署会**整体对齐** sections：缺的写、旧的改、多余的删。

评分口径写进 `skill-ratings.json`（可复算）：base 5 + `references/` +1 + 带可执行脚本 +1 +
`description` ≥80 字符 +1 + 正文 ≥2500 字符 +1 + 含代码块 +1，夹在 1..10。
它是**自足度**不是质量论断；人工用 `skill_tool.py rate --set <技能> <分>` 覆盖并记入 `manual`，
`--seed` 不会盖掉人工值。

## 三、一个必要的口径澄清

进系统提示词的只有菜单技能的 **名字 + 描述 + 路径**（实测 609 字符 ≈ 90 tokens/轮）；
菜单正文与分片都是模型**按需读**的。所以分片省的不是每轮常驻开销，而是**每次读菜单的体积**
——技能库涨到几百个模块时，读「菜单 + 一个相关分片」远小于读一张几万字符的大表，
也不会撞上单文件读取上限。

## 四、其他改动

- `skill_tool.py rate`：`--seed` / `--set` / `--list` / `--check` / `--threshold`
- `skill_tool.py contract`：多一行「评分 已评 N/N ｜ 类目内超过 X 个模块就分片」；覆盖不全只告警不拦
- 随包资源 18 → **19 项**（新增 `skill-ratings.json`，同时进 `bj_tool.spec` 与 `deploy-contract.json`）
- 修：技能库页教程第 4 步指向已不存在的 `_table`（技能库页早已改成卡片流）→ 改指卡片流容器
- `tests/verify_menu.py`（新，25 项）：评分列 / 分片 / **陈旧分片清理** / `-Check` 覆盖分片 / 缺评分降级

## 五、验证

- `tests/run_all.py` → **13/13 全过**（含新菜单套件 25/25）
- `skill_tool.py contract` → 契约与仓库一致（随包资源 19 项齐全、评分 65/65）
- `PJ_BUNDLE_CHECK=1` → `ok=true`、技能 65；`PJ_UI_SELFTEST=1` → 退出码 0
- 用**打包内**的 injector 在沙箱跑极简模式 → `RESULT: OK`，菜单列 65 个模块、拆出 1 个分片
- 实测：65 模块菜单 6,615 字符；「逆向 / 二进制」15 个模块拆成 `01-radare2.md`（1,717 字节）

## 六、已知边界

- 分片阈值默认 12，可用 `rate --threshold N` 或 `inject.ps1 -ShardThreshold` 覆盖
- 完整模式下 65 个模块 ≈ 7k tokens/轮（固定开销）；模块规模上去后建议用极简模式
- `disable-model-invocation` 只在 Pi 上实测过，其他客户端不确定时先用 `full`
- 评分是自动生成的自足度：想按"实际好不好用"排序，用 `rate --set` 手工覆盖
