# Code Quality Gate · 工程自检评分门禁

## 定位

对**一个已完成的代码改动 / 功能交付**做交付前自检。与 lint/测试工具互补：
工具管机器可测的（复杂度/覆盖），本 skill 管**工程判断层**（改动是否收敛、
能不能定位、有没有越界、敢不敢签字）。

**判定原则：确定性优先。** 凡是能用命令/文件验证的，先跑命令拿事实再填表；
拿不到事实的项，如实标"未验证"，不许编造通过。

## 使用时机

- 一轮功能开发完成、准备说"做完了"之前
- 修 bug 后确认没有牵连伤害
- 接手别人项目、修改他人代码之前/之后
- Reviewer 打回后的整改自检

不适用：还在写一半的代码、纯文档改动（跳过代码维度打分即可）。

## 执行流程

### 第 0 步 · 圈定范围

先确定三件事，写进报告头：

```
评定对象：<本次改动涉及的源码文件（带路径），改动前后行数，新增/修改的测试文件与用例数>
范围边界：<离线/在线；是否只读；是否零生产路径改动；明确"不检查什么">
```

没有明确范围的评分无效。禁止"整个项目大概过一遍"。

### 第 1 步 · 确定性检查（先跑命令，再填表）

以下每项先给出**验证命令**，跑完再填是/否：

| # | 检查 | 验证手段（按项目类型取用） |
|---|------|--------------------------|
| G1 | 改动收敛 | `git diff --stat`：改动文件数、是否只在预期文件内 |
| G2 | 可定位 | 出错路径是否有 error_code / 日志 / 结构化 reasons |
| G3 | 命名一致 | 抽查新增常量/函数命名与既有风格比对 |
| G4 | 测试覆盖 | 跑测试：新增用例数、通过数；有无活动门禁（fail-closed） |
| G5 | 一键构建 | 干净环境语法检查 `py_compile` / `uv sync` / `npm ci` 等 |
| G6 | 依赖锁定 | lockfile 是否更新（uv.lock / package-lock / poetry.lock） |
| G7 | 模块边界 | import 检查脚本 / 架构规则（domain 不碰框架等） |
| G8 | 不动他人代码 | `git diff` 中是否出现与本次无关的文件改动 |

### 第 2 步 · 九问评分表

输出为表格。每行：`# | 问题 | 是/否（得分） | 证据`。
**证据列必须写命令输出或文件:行号**，写"我觉得没问题"不给分。

| # | 问题 | 分 |
|---|------|----|
| 1 | 改一个功能只改 1-2 个文件吗？（改动收敛，不牵连全身） | 1 |
| 2 | 出 Bug 能快速定位到 operation_id / frame / 文件:行号 吗？（可定位性） | 1 |
| 3 | 代码有统一命名风格吗？（常量大写、命名与既有风格一致） | 1 |
| 4 | 核心逻辑有测试覆盖吗？（新增用例 + 既有回归全过 + 有 fail-closed 门禁） | 1 |
| 5 | 能一键构建并跑起来吗？（干净环境、无手工步骤） | 1 |
| 6 | 出错时有清晰错误码和日志吗？（error_code + logger，不是裸 print） | 1 |
| 7 | 依赖版本锁定了吗？（lockfile 更新，无未声明依赖） | 1 |
| 8 | 模块边界清晰吗？（分层不越界 import，单文件职责） | 1 |
| 9 | 敢不问原作者就直接改代码吗？（文档/契约/测试三者一致，边界放心） | 1 |

### 第 3 步 · 扣分项（从 10 分里扣，与上面 9 问独立）

逐项检查，命中才扣，并在报告里写明扣分理由：

| 扣分项 | 幅度 | 判定 |
|--------|------|------|
| 超长函数/类 | -2 | 单文件 >1000 行，或单函数 >80 行且无法用"集中审计"理由豁免 |
| 魔法数字/硬编码 | -2 | 关键期望值未抽成常量（已有常量的不扣） |
| 零测试/不稳定测试 | -3 | 核心逻辑无测试，或测试会被本次改动打挂 |
| 越界修改 | -3 | 改了与本次无关的模块/文件 |
| 密钥/敏感信息 | -5 | 硬编码凭据、token、内网地址入库 |

豁免规则：如果超长是**有意的**（例如把全部审计逻辑集中在一个只读模块便于隔离），
可以在扣分记录里写明理由并注明"豁免申请"，但分数照扣——豁免只影响结论措辞，不影响分。

### 第 4 步 · 未证明项（显式列出，不许沉默）

评分之外，把**本次没能证明的事项**逐条列出，格式：

```
- 张力对照：NOT_PROVEN（缺独立抓帧数据）
- 控制器归因：待归因（需要 X 数据才能定）
```

分类标签：`NOT_PROVEN`（证据不足）/ `待归因`（需要外部输入）/ `CAPTURE_LIMITATION`（受环境限制）。
**未证明项不扣分也不加分，但必须在"下一步"里有对应动作**，否则不许通过。

### 第 5 步 · 结论与下一步

```
本轮得分：N/10（≥7 门禁通过；≤6 打回）
扣分记录：（逐项，或"无扣分"）
未证明项：（逐条，或"无"）
结论：一句话（例如：实现为离线只读分析，无生产路径改动；下一步等待 Reviewer 核查）
下一步：具体到"等谁/做什么/触发条件"
```

通过线：**≥7 分**。8-9 分=小有瑕疵；10 分=满分；≤6=打回并列出必改项。

## 输出格式

最终报告按以下结构（Markdown）：

```markdown
# <项目/改动名> 自检（<日期> <迭代号>）

> 评定对象：<文件/行数/用例数>
> 范围边界：<离线/只读/零生产改动等>

| # | 问题 | 是/否 | 备注（证据） |
|---|------|-------|------|
| 1 | ... | 是 (1分) | <命令或 file:line> |
...

**本轮得分：N/10**（≥7 分门禁通过）

**扣分记录：**
- 项：扣分值（理由）
...

**未证明项：**
- 项：NOT_PROVEN / 待归因（说明）

**结论与下一步：**
<一段话>。下一步：<动作>。
```

## 红线

- 先跑命令后填表；没跑的命令不许写"已验证"
- 拿不到证据的项写"未验证"并进未证明项，不许默写"是"
- 评分对象必须先圈定范围；范围不明先问一句，问了再评
- 报告里的每一个"是"都要能被 Reviewer 用一条命令复现
- 结论里的下一步必须具体（谁/做什么/何时），不许写"后续优化"
